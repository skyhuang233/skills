# 软件工程原则

这是一份**参考**，不是一次会话，也不是教程。任何 skill 都可以引用它取词，不需要「运行」它。

每条原则给出：原则本身 → 失败例 → 正例 → 一句话核心。它回答「这个设计对不对」，不回答「这份代码在本仓库里合不合规」——后者以仓库文档化的编码标准为准，仓库标准优先。

## 一、错误处理与正确性

### 1. 让非法状态无法被表示（Make Illegal States Unrepresentable）

与其在运行时不断检查某种状态是否合法，不如在设计上让这种状态根本无法产生。

**失败例**——订单状态用几个独立布尔值表示：

```typescript
interface Order {
  isPaid: boolean;
  isCancelled: boolean;
  isShipped: boolean;
}
```

它允许产生「既取消又发货」「未付款却已发货」等不合理的组合。

**正例**——用明确的状态模型：

```typescript
type Order =
  | { status: "pending" }
  | { status: "paid"; paidAt: Date }
  | { status: "shipped"; trackingId: string }
  | { status: "cancelled"; reason: string };
```

这并不能自动保证所有状态转换合法，但至少排除了不少无效状态组合。

**核心：**把正确性从程序员的自觉，转移到程序结构和类型系统中。

### 2. 尽早失败，而不是带着错误继续运行（Fail Fast）

如果一个错误已经使系统无法保证正确性，那么继续运行往往比立即失败更危险。

**失败例**——服务启动时发现支付服务的密钥没有配置，于是用一个默认空字符串继续启动，直到用户付款时才暴露错误。

**正例**——在启动时检查配置，并明确报告启动失败。

有一个重要区别：

- 如果错误影响关键不变量，应尽早失败；
- 如果错误是可预期、可恢复的局部故障，应尽量隔离影响。

**核心：**错误越晚暴露，其原因与后果之间的距离通常越远，排查成本也越高。

### 3. 不要用默认值掩盖数据异常

只有当默认值具有真实业务语义时，使用默认值才是正确的。

**失败例：**

```python
price = product.get("price", 0)
```

这把「缺少价格」错误地解释成「价格为零」。

**正例**——如果价格字段是必需的，就拒绝不完整的数据，而不是静默生成一个合法但错误的值。反过来，如果某个设置本来就允许缺省，默认值完全合理。

**核心：**缺失、不存在、未知、零值，往往是不同的业务概念，不应该随意混为一谈。

### 4. 解析而非校验（Parse, don't validate）

在系统边界**一次性**把无结构输入转成有类型的结构，而不是在同一份数据上到处重复校验。校验的产物是布尔值，它不携带信息；解析的产物是类型，之后所有代码都只需要面对合法值。

**失败例**——同一个邮箱字段在 controller、service、repository 三层各校验一次，每层都用 `str` 传递，任何一层忘记校验就漏进非法值。

**正例**——在边界解析成一个自带约束的类型：

```python
@dataclass(frozen=True)
class Email:
    address: str

    def __post_init__(self) -> None:
        if "@" not in self.address:
            raise ValueError(f"not an email: {self.address!r}")

def parse_email(raw: str) -> Email:   # 边界处唯一一次校验
    return Email(raw)
```

下游所有函数的签名都写 `Email`，不再需要重复校验，也不可能传进非法值。

**核心：**把校验推到边界一次做完，让类型系统承载「已校验」这个事实。

## 二、抽象与系统设计

### 5. 错误的抽象比适度的重复更昂贵

不要仅仅因为两段代码看起来相似，就急于把它们抽象到一起。

**失败例**——两个模块都有一个计算折扣的方法。它们当前恰好使用相同公式，但一个遵循会员政策，另一个遵循促销政策。立即抽象为一个共享方法，未来两个政策独立演变时，就会出现大量参数和条件分支。

**正例**——适度保留重复。真正的抽象等到两条规则的共同部分稳定下来再做。

**核心：**真正值得抽象的是稳定且一致的业务规则，而不是偶然相似的代码结构。

这也是 DRY（Don't Repeat Yourself）经常被误解的地方：DRY 主要反对的是知识和规则的重复，而不是所有形式的代码重复。

### 6. 好的抽象应该隐藏复杂性，而不是转移复杂性

如果一个抽象要求使用者理解它内部的大部分实现细节，那么这个抽象可能没有发挥应有的作用。

**失败例：**

```python
paymentService.pay(order, True, False, "sync", 3, "strict")
```

调用者必须知道每个布尔和字符串的含义。

**正例：**

```python
paymentService.pay(order)
```

必要的业务选择应该有自己的名字和类型，而不是退化成位置参数。

第二种接口也可能是在暴露必要的业务选择。问题不在于参数数量本身，而在于调用者是否被迫了解本应由内部负责的细节。

**核心：**抽象的价值在于减少使用者必须掌握的知识。

### 7. 模块之间的依赖应该指向更稳定的部分（Stable Dependencies Principle）

经常变化的模块，不应该迫使稳定的核心业务逻辑跟着一起变化。

**失败例**——订单领域逻辑直接 `import` 某个支付供应商的 SDK。更换供应商就要改订单核心逻辑，测试也要联网。

**正例**——领域逻辑依赖一个内部定义的 `PaymentGateway` 接口，由外部适配器实现它。更换支付供应商时，订单核心逻辑无需修改。

这也是依赖倒置原则（DIP）和六边形架构的重要动机。

**核心：**让变化停留在变化发生的位置，不要让它在整个系统中传播。

### 8. 一个模块应该对外暴露能力，而不是暴露内部结构

模块的边界应该由它承担的责任定义，而不是由它保存了哪些数据定义。

**失败例：**

```python
account.balance -= 100
```

余额、透支规则、审计记录散落在所有调用方。

**正例：**

```python
account.withdraw(100)
```

后一种设计可以在同一个地方维护余额、透支规则、审计记录等不变量。

**核心：**数据和维护数据正确性的规则应尽可能封装在同一个责任边界内。

### 9. 名字揭示意图

名字是接口的一部分：调用者先读到的就是它。一个名字说不清「它做什么」或「它存什么」，说明设计本身还没有想清楚——找不到诚实的名字，通常是概念还没收敛的信号。

**失败例：**

```python
data = fetch(x)        # 拿到的是什么？要读三处调用点才知道
handle(item)           # 怎么 handle？
tmp = compute(a, b)
```

**正例：**

```python
unpaid_invoices = load_unpaid_invoices(customer_id)
retry_payment(invoice)
tax = compute_tax(net_amount)
```

命名是廉价的：改一个名字只花几秒。所以当名字难以取出时，不要用一个模糊的名字绕过去，先回到设计上问「这个东西到底是什么」。

**核心：**找不到诚实的名字，通常说明设计是浑的；名字难起的时候改结构，而不是改名字。

## 三、并发、分布式系统与可靠性

### 10. 任何跨越进程或网络边界的操作，都必须假设它可能失败

本地函数调用和远程服务调用，虽然可能拥有类似的语法，却具有完全不同的可靠性语义。

**失败例：**

```python
result = payment_service.charge(order)
```

这行代码可能遭遇：

- 网络超时；
- 远程服务不可用；
- 请求已经成功，但响应丢失；
- 对方仍在处理，而本地已经放弃等待。

**正例**——远程调用需要考虑超时、错误分类、重试、幂等性和故障隔离，并在接口上把这些语义写清楚。

**核心：**网络调用不只是一个比较慢的函数调用。

### 11. 只有当重复执行是安全的，重试才真正有意义

重试不是一种通用的错误恢复手段，它本身可能制造新的错误。

**失败例**——向支付服务发送扣款请求，30 秒后发生超时。超时并不意味着扣款失败。直接重试，用户可能被扣款两次。

**正例**——引入幂等键（Idempotency Key），让相同业务操作的重复请求可以被识别；同时明确哪些错误可重试、重试次数和退避策略。

**核心：**重试解决的是暂时性故障，但必须先解决重复执行的正确性问题。

### 12. 超时不等于取消，取消不等于回滚

一个操作在调用方看来已经结束，并不意味着它在整个系统中已经停止或撤销。

**失败例：**

1. A 服务请求 B 创建订单；
2. A 等待 5 秒后超时；
3. B 在第 6 秒创建订单成功；
4. A 认为调用失败，发起第二次创建。

这时可能产生两个订单。

**正例**——区分三个概念：

- **Timeout**：调用方不再等待；
- **Cancellation**：尝试通知任务停止；
- **Rollback / Compensation**：撤销或补偿已经产生的业务影响。

**核心：**一次调用的生命周期，不一定等于一次业务操作的生命周期。

### 13. 没有资源上限的系统，最终会在压力下失控

只要输入速率有可能持续超过处理速率，无界缓冲就不是解决方案，而是在延迟故障。

**失败例**——一个消费者每秒只能处理 1,000 条消息，但生产者每秒持续发送 2,000 条。如果无限制地把消息存入内存，内存占用会持续增加。

**正例**——采用背压（Backpressure）、有界队列、限流、负载削减等机制，并明确规定超限时发生什么。

**核心：**系统必须明确规定，当工作量超过处理能力时，应该发生什么。

### 14. 共享可变状态是并发缺陷的根源

并发正确性应该靠结构保证，而不是靠「记得加锁」的纪律。多个执行流同时读写同一块可变状态时，正确性依赖调用顺序，而调用顺序不在任何一处的代码里。

**失败例：**

```python
class Counter:
    def __init__(self) -> None:
        self.value = 0      # 多个线程共享

    def increment(self) -> None:
        self.value += 1     # 读—改—写，不是原子操作
```

两个线程各加 1000 次，结果常常小于 2000。更麻烦的是：这个类本身看不出不能并发使用。

**正例**——用不可变数据、明确的所有权或消息传递划清边界。要共享状态时，把它收敛到一个拥有者、一个明确的同步点：

```python
class Counter:
    def __init__(self) -> None:
        self._lock = threading.Lock()
        self._value = 0

    def increment(self) -> None:
        with self._lock:
            self._value += 1
```

**核心：**并发正确性靠结构保证，不靠加锁纪律；先问能不能不共享，再问怎么同步。

## 四、测试、可维护性与可观测性

### 15. 测试应该验证行为，而不是复制实现

如果代码内部进行了重构，但对外行为没有改变，那么测试通常不应该因此大面积失败。

**失败例**——断言内部调用的顺序或次数、测试私有方法、用快照固化内部数据结构。重构一次，几十个测试变红，但没有任何行为变化。

**正例**——测试一个排序函数时，关注：

- 输出是否有序；
- 是否保留所有输入元素；
- 相等元素的相对顺序是否符合稳定性约定。

而不是关注它内部用了快速排序还是归并排序。

对于算法库等特定场景，性能与算法性质本身也可能是测试契约的一部分。

**核心：**测试应该保护系统的契约，而不是冻结系统的内部实现。

### 16. 一个系统无法观测的问题，通常也无法被可靠地诊断

能够处理错误是一回事，能够知道错误为什么发生是另一回事。

**失败例**——日志只输出：

```text
Payment failed
```

虽然比没有日志好，但对于排查复杂支付故障远远不够。

**正例**——结构化日志包含请求 ID、订单 ID、错误类别、远程服务名称、耗时等信息，同时避免记录敏感支付信息。对于复杂系统，还需要结合指标（Metrics）、日志（Logs）和分布式追踪（Traces）。

**核心：**可观测性不是上线后的附加功能，而是系统可靠性设计的一部分。

### 17. 不要优化你尚未测量的瓶颈

优化应该以可观测的性能问题为依据，而不是以代码看起来是否高效为依据。

**失败例**——一个接口耗时 800 毫秒。开发者花了三天优化内存分配，节省了 2 毫秒，却没有发现其中 700 毫秒来自数据库查询。

**正例**——按这个顺序工作：测量 → 定位瓶颈 → 制定假设 → 优化 → 再次测量。

这不意味着应该忽略显而易见的算法复杂度或资源风险。

**核心：**性能工程是一种基于证据的工程活动，而不是关于代码风格的猜测。

### 18. 时间和随机性必须可注入

直接读系统时钟和全局随机会让行为不可复现、不可测试。一个函数只要自己调用 `now()` 或 `random()`，它的输出就不再是输入的函数。

**失败例：**

```python
def is_expired(token) -> bool:
    return datetime.now() > token.expires_at    # 不可测：结果取决于运行时刻

def pick_shard(key: str) -> int:
    return random.randint(0, 9)                 # 不可复现：无法断言
```

**正例**——把时钟和随机源作为依赖传入，在生产环境注入真实实现，在测试中注入固定值：

```python
def is_expired(token, now: datetime) -> bool:
    return now > token.expires_at

def pick_shard(rng: random.Random, key: str) -> int:
    return rng.randrange(10)
```

**核心：**行为应该是其显式输入的函数；时间和随机性也是输入。

## 五、工程决策与复杂度管理

### 19. 不要为尚未出现的需求引入确定的复杂度（YAGNI）

不确定的未来需求，不应该无条件地成为今天增加复杂度的理由。

**失败例**——一个业务当前只有一种存储实现。为了将来可能支持十种数据库，提前设计一个复杂的存储插件框架，未必是正确选择，因为未来真正变化的方向可能根本不是数据库类型。

**正例**——保持模块边界清晰，在实际需求出现时再扩展。

**核心：**未来的灵活性有成本，而且过早预测变化方向经常出错。

### 20. 简单不等于代码少，而是需要理解的状态和规则少

判断设计是否简单，不应该只看代码行数，而应该看理解它需要多少上下文。

**失败例**——把 200 行业务逻辑压缩成一个高度通用的 30 行函数。它可能只是把显式代码转换成了隐式约定：阅读者需要在脑中展开这个通用函数才能知道当前这条路径做什么。

**正例**——减少真正产生认知负担的东西：

- 不必要的状态数量；
- 模块之间的隐藏依赖；
- 业务规则的分散程度；
- 阅读代码时需要同时记住的前提条件。

**核心：**软件设计的目标不是最小化代码量，而是最小化实现正确行为所需的复杂度。

### 21. 显式优于隐式

依赖、顺序、失败模式都应该写在签名和结构里，而不是靠调用者的记忆或团队约定。隐式约定在写下的那一刻是对的，在下一个改动之后就不一定了，而且没有任何东西会提醒。

**失败例：**

```python
send_report(user_id)    # 依赖模块级配置、必须在前一次 flush 之后调用、
                        # 失败时静默返回 False——三条前提都只活在注释或口头约定里
```

**正例：**

```python
def send_report(user_id: UserId, *, at: datetime, dry_run: bool = False) -> ReportId:
    """失败时抛出 ReportDeliveryError。"""
```

依赖、时点和失败模式都进入签名：读者不必先学会这个项目的规矩，就能正确调用它。

**核心：**把读者必须记住的前提，换成代码本身能说清的前提。

## 三条根本判断标准

上面的原则背后是三个更根本的判断标准。遇到原则没有直接覆盖的情况时，回到它们：

**1. 谁拥有做出正确决策所需的信息**
只有掌握足够上下文的一层，才应该决定如何恢复错误、改变状态或者执行某项业务规则。信息不在这一层，这一层就不该做这个决定。

**2. 如何让错误和变化的影响尽量局部化**
通过明确边界、封装不变量、隔离副作用和控制依赖方向，避免单点问题扩散到整个系统。

**3. 这个设计是在消除复杂度，还是仅仅转移复杂度**
抽象、缓存、重试、框架和中间件，都可能降低某些复杂度，同时引入新的复杂度。关键是权衡是否值得。
