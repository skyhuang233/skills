# 测试驱动开发

TDD 就是红 → 绿循环。这份参考让这个循环产出值得留下的测试：什么算好测试、测什么、从哪测、
有哪些反模式、循环本身有哪些规则。每一节都在每一次循环中生效——在循环前和循环中查阅它们，
而不是等循环结束。

## 什么算好测试

测试通过公开入口验证行为，而不是验证实现细节。代码可以整个换掉，测试不该跟着换。好测试
读起来像一份规格说明——「用户可以用有效购物车结账」明确告诉你存在什么能力——因为它陈述的
是契约，而不是内部结构。

示例见 [tests.md](tests.md)，mock 准则见 [mocking.md](mocking.md)。

## 契约——测什么，以及从哪测

**契约**是调用者或领域关心、且不依赖内部结构的陈述，例如「恢复后的状态等于保存前的状态」、
「query 放不下时立即失败」。**入口**是你在其上测试的调用点。测试保护的是契约，入口只是
当前选中的观察位置。

**先商定契约，再写测试。** 写任何测试前，先列出本次要保护的契约，并与用户确认。确认的是
契约陈述，不是函数名、模块名或 patch 点；用户对这份清单表态——认可，或划掉某条。你不可能
测完所有东西——事先商定契约，就是让测试精力落在关键路径和复杂逻辑上。

每条契约至少写明：

- **公开入口**——从哪个调用点观察；
- **调用者**——谁依赖它；
- **可观察结果**——返回值、通过公开入口读回的状态，或系统边界上的副作用。可观察结果不能是
  内部调用次数、调用顺序或私有函数。

**入口在写每个测试时临时选，取当前最外层、跑得够快的那个。** 入口以后可以换；换入口时测试
跟着搬，断言不变。

**说不出契约的部分，就是还在探索的部分，不写测试。** 不为一个猜测冻结测试结构。

「探索中」按**调用者关心什么**判定，不按接口名稳不稳判定：调用者关心什么还没定，才算探索；
调用者已经知道、只是接口名字还会变，不算——那正是契约测试要保护的情形。

## 反模式

- **实现耦合**——mock 内部协作者、测试私有方法，或通过旁路验证（绕过接口直接查数据库）。
  征兆：你重构了代码，行为没有变化，测试却红了。
- **同义反复**——断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`，按同样
  算法手工推导的快照，把一个常量断言成它自己），于是它按构造必然通过，永远不可能与代码
  不一致。期望值必须来自独立的事实来源——一个已知正确的字面量、一个手算示例、规格本身。
- **横向切片**——先写完所有测试，再写所有实现。批量测试验证的是*想象中*的行为：你测的是
  事物的*形状*而不是面向用户的行为，测试对真实变化变得不敏感，而且你还不理解实现就先把
  测试结构钉死了。改为按**纵向切片**推进——一个测试 → 一个实现 → 重复，每个测试都是一颗
  **曳光弹**，它回应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好让它通过的最少代码。不要预判后续测试，也不要
  添加投机性的功能。
- **一次一个切片。** 每个循环一个契约、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于审查阶段（见 `code-review` skill），不属于红 → 绿的实施
  循环。
