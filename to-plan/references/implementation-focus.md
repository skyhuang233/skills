# Design Blocks and Contract Depth

本文件控制详细设计讨论什么、定义到什么程度，以及何时写回活计划。核心单位是**设计块**：
一条主流程、一个核心数据模型，或被多条流程共享的执行边界。

## 先建立挂靠关系

在工作上下文维护覆盖账本，不把它输出到计划：

| 概要流程或实体 | 当前代码接缝 | 已确认目标 | 本设计块 | 需要固定的契约 |
|---|---|---|---|---|

每个详细设计块必须回答它细化了概要中的什么。一个关系同时依赖 orchestration 和 adapter 时，
两侧接缝在同一设计块中闭合；复用且保持不变的组件只在拥有该箭头或数据的地方引用。

## 设计块门槛

符合至少一项时才展开详细设计：

- 改变责任归属、系统边界、跨模块接口、持久化语义或配置语义；
- 固定状态转换、并发、重试、幂等、完成条件或信任边界；
- 引入 provider/wire adapter、兼容迁移、双链路风险或不可逆资源生命周期；
- 属于重要、意外、高风险、复杂或易变的实现接缝。

第二、三条是**触发详细设计的信号，不是必须产出防御机制的清单**。「固定重试、幂等、信任边界
或不可逆生命周期」的结论可以是「不处理」或「前置校验 + fail-fast」。每个防御性机制按
[最小充分机制](minimal-mechanism.md)判必要性：先证明威胁在本设计边界内真实存在，必要性未证实
的不进入计划；必要性成立时取阶梯最低一级。计划只写入用户已确认的目标设计，不写「暂不处理」
的占位说明。

文件枚举、测试替身、命名清理、普通 wiring 和局部控制流并入其真正 owner，或留给实施者。

## 按认知层级定义数据

数据结构先回答系统问题，再回答 SQL 或 Go 问题：

| 层级 | 必须回答 | 首选表达 |
|---|---|---|
| 概要数据模型 | 有哪些存储和实体、各自用途、身份、关系、核心状态 | ER 图 + 实体概览表 |
| 流程中的数据 | 哪一步创建、读取、更新哪个实体，字段组或状态如何变化 | 带数据效果的时序图 |
| 详细持久化契约 | 影响正确性的字段类型、null/default、主键/唯一约束、索引与状态不变量 | schema 表或短 DDL |
| 领域或 wire 载荷 | 来源字段到 canonical 字段、必选性、规范化与拒绝规则 | 字段映射表或短 payload |
| 代码数据类型 | 跨模块共享且会改变调用方实现的公开类型 | 短 type/interface |

概要阶段可以先确认“准备新增哪些表、重要字段和状态”；精确列类型、字节编码和方法签名在它们
确实影响实现选择时进入详细设计。

## 按变更类型固定最小契约

| 变更类型 | 设计块必须回答 | 首选表达 |
|---|---|---|
| 跨模块接口 | owner、调用方向、最小操作/类型、生命周期与错误边界 | 责任表 + 短 interface |
| 状态与并发 | 触发、条件、状态转换、持久化效果和执行 owner | 状态表或时序图 |
| adapter / reconciler | 受管资源、稳定身份、所需 capability、read-back 和 desired-state 动作 | capability 矩阵 |
| parser / classifier | raw 字段到 typed 字段再到领域效果；影响正确性的 grammar 边界 | 映射表，必要时补 grammar |
| 配置与秘密 | key、来源、消费者、生命周期、回退和暴露边界 | 配置或身份映射表 |
| 迁移与兼容 | before/after owner、共存边界、删除条件和保持不变的消费者 | before/after 表 |
| 可观测性 | 产生信号的组件、signal、单位、低基数 labels 与语义 | signal 表 |

## 确认来源门槛

为每个目标契约标记来源类别：

| 类别 | 处理方式 |
|---|---|
| 当前实现事实 | 用当前目标分支校准，只能描述现状或复用接缝 |
| 已确认目标设计 | 来自用户明确确认、已采纳 ADR 或权威外部契约，写入计划 |
| agent 推荐 | 作为一个带推荐答案的问题提交用户，确认后升级为目标设计 |
| 缺失外部事实 | 在计划外报告缺失输入，取得事实后再写目标契约 |

权威外部契约只确认它明文规定的 wire 或 provider 约束；从这些约束派生出的内部 schema、接口、
状态或配置仍属于 agent 推荐，需要用户明确确认或已采纳 ADR。

旧计划、示例和旧分支只能提供线索。一个精确格式即使技术上合理，也不能用“实施者无需重新
设计”作为自行决定它的理由。

## 阶段性回写

设计块达到以下条件后立即写回活计划：用户已确认目标选择；相关当前事实已核对；数据、状态、
接口和 owner 相互一致；该块能够独立解释。写回时同步修改概要图、数据模型、时序和详细段落，
不在文末追加一块孤立说明。

回写后只读标题、图、表、时序箭头和条目首句。它们应直接暴露重要决定；三组以上同维信息
转换为表格，连续状态变化转换为状态表或时序图，局部算法的篇幅不超过其输入、输出和错误
边界。

**完成条件：**每个 changed 概要元素和关系都有实现 owner；每个精确目标契约都有确认来源；
计划中没有必要性未证实的防御机制，每个保留的机制都能说明它防的威胁和所处的阶梯级；每个
详细块都沿概要主线增加可实施信息，没有漂浮细节。
