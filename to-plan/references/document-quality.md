# Plan Document Quality Standard

本文件是 plan 的输出契约。计划的价值是让首次阅读者先建立完整心智模型，再沿同一模型进入
重要细节。篇幅由问题复杂度决定；清晰度来自信息顺序和相互连接，而不是固定文件数量。

## 从概要到详细的阅读顺序

按任务需要选择以下内容，并保持它们的依赖顺序：

1. **定位与能力**：一句话边界和少量核心能力；
2. **总体设计**：参与者、系统边界、核心组件和端到端主流程；
3. **数据模型**：新增或改变的存储、实体关系、稳定身份、重要字段与核心状态；
4. **端到端时序**：沿主流程标出关键读写、状态转换和完成结果；
5. **详细设计**：接口、并发、重试、幂等、配置或生命周期中会改变实现选择的部分；
6. **实现定位**：模块、稳定路径或公开符号及其责任变化。

这是一条认知路径，不是固定目录。已有文档可以采用更贴合领域的标题；同一读者能够连续理解
时保持一份文档，读者、owner 或生命周期形成独立评审问题时自然分开。

## 图、数据与细节必须相连

- 总图中的组件名成为后续数据 owner、时序参与者和实现模块的统一名称；
- 总图中的每条重要箭头由时序展开，箭头使用动作或载荷命名；
- 每个持久化实体都说明用途、身份、关系和核心状态；重要字段按语义成组展示；
- 时序中的数据操作写出目标实体及效果，例如 `INSERT task(status=pending)` 或
  `UPDATE task → completed`；
- 状态表、接口、配置和代码定位明确细化哪条主流程、哪个实体或哪个边界；
- 新增细节后回读概要；名称、方向或状态发生变化时同步修改所有相关视图。

一个章节如果无法挂到概要中的流程、数据或边界，就是设计尚未连贯的信号，而不是需要增加
一段背景文字的信号。

## 选择表达介质

按以下优先级选择能完整保留含义的最短载体：

1. Mermaid：边界、数据流、实体关系、时序、状态和部署关系；
2. 表格：字段、映射、责任、差异、状态转换和配置；
3. 短列表：有限规则和实现动作；
4. 代码块：已经确认的精确接口、载荷或配置形状；
5. 正文：连接前四种形式所需的一句话说明。

每张图只回答一个问题并保持同一抽象层级。主图优先建立整体，ER 图回答数据关系，时序图回答
运行过程；详细算法不能挤进总体图。三项以上共享同一维度的信息用表格表达。

## 控制细节与篇幅

一个细节只有在改变系统心智模型或实现选择时才进入计划。优先保留责任、数据、状态、跨边界
接口、并发、幂等、失败语义和不可逆生命周期。稳定路径和公开符号用于定位；局部变量、内部
helper、普通 wiring、完整文件清单和可从源码自然推出的控制流留给实施者。

涉及精确目标契约时，完整应用[设计块与契约深度](implementation-focus.md)中的“确认来源门槛”。

计划直接呈现所选设计。设计形成过程、ADR 理由、证据清单、测试与验证方案、人工门槛、生产
判定、风险登记和 Issue 拆分属于工作过程或后续材料。

## 可读性与删除测试

- 标题构成从概要到详细的信息地图；
- 结论放在表头、条目和句子开头；一条只承担一个主要意思；
- 使用稳定领域术语，代码名只定位实现或固定公开契约；
- 用户建议形成流程、数据、状态、边界或实现动作后再进入文档；
- 图表已经表达的含义由图表承担，正文只补缺失关系；
- 删除一段后仍能理解并实施同一重要变化时，删除该段。
