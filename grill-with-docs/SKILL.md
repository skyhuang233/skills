# 从概要到详细共创设计

同时使用 `/grilling` 和 `$to-plan`：`/grilling` 负责一次只解决一个用户决策，`$to-plan` 负责
维护同一份活计划。计划在讨论中逐块成形，而不是在访谈结束后批量重建。

把用户对一个完整设计块的确认视为该块已经达到 shared understanding：此时只更新设计文档。

设计取舍参照 `software-engineering-principle` 取词。它在以下环节直接生效：

- 第 1、4、8 条约束数据模型的形状与边界解析——边界的结构、内部结构对外的暴露面；
- 第 2、3 条约束 fail-fast 结论——什么时候必须尽早失败，什么时候不能靠默认值掩盖；
- 第 5、6、7 条约束抽象与依赖方向——要不要抽象、抽象后复杂性去了哪里、依赖指向谁。

## 1. 建立设计画布

在第一个问题前阅读现有计划、当前目标分支的相关源码与配置。事实从环境取得，用户只裁决
目标设计。

先向用户描述一版可修正的概要设计：系统边界与能力、从触发到结果的主要端到端流程、组件
责任、需要持久化的核心实体及其状态。使用领域语言和少量图表，不从局部接口、字段类型或
异常分支开始。请用户先确认或修正这张整体地图。

**完成条件：**用户已明确确认或修正一份覆盖系统能力、主要流程、执行者和核心数据变化的
概要；四项均有可引用的确认。

## 2. 收敛概要设计

按依赖顺序一次询问一个决策，并给出推荐答案：

1. 系统范围、能力和主流程；
2. 数据存储、实体关系、稳定身份和生命周期状态；
3. 每条主流程中的关键写入、更新和完成结果；
4. 会改变上述流程的执行归属、并发边界或外部系统边界。

每个推荐答案先称**实现重量**——它引入多少新抽象、新代码路径和维护面。提议新机制前，
先清点现有框架和代码库已经提供的能力；能用已有能力满足的需求直接复用。当两个选项
达成相同目标时，推荐实现重量更低的；当更完备的选项带来不成比例的重量，向用户明示
代价，让用户在充分了解实现重量的前提下裁决。

**但实现重量只衡量代价，不衡量需求——必须先过必要性门槛。** 鉴权、新增持久化实体、重试
与补偿、provider/wire 抽象层这类防御性机制，都是「小接口、少行数、局部位置」，按重量衡量
永远通过。完整阅读[最小充分机制](references/minimal-mechanism.md)，按它判断每个防御性提议：

- 先问它防的具体威胁是什么、触发条件在本设计边界内是否真实存在；必要性未证实就直接删除，
  不进入重量对比；
- 必要性成立时，从**防御阶梯**取最低一级：不处理 → 前置校验 + fail-fast → 让非法状态不可
  表示或复用现有 seam → 补偿/重试/回滚。**fail-fast 是完整答案，不是「没做防御」**；
- 提出重试、补偿、回滚或聚合前，先说明前置校验为什么不通过、为什么 1 级不够；
- 不要为「更完备」保留必要性未证实的机制，也不要在计划里留它的「暂不处理」说明。

同一份阶梯适用于计划评审：一个防御性机制若只有重量论证，没有需求论证，就是待删除项。

概念本身模糊时，就地把它磨利，不要跳过去：

- **磨利模糊术语**——一个词承载两种含义时，逼出一个规范用词，并说出另一个含义该叫什么；
- **构造边界场景**——用具体场景压力测试概念之间的界线：一个例子落在界线的哪一侧？
  哪一侧的例子同时符合两个定义？

这两项动作的结论只进入当前 plan，不依赖任何全局文档。跨设计块的用词一致性在本次 plan
内部核对。

一个问题只有在用户确认、所依赖事实已经核对、且与先前结论没有矛盾时才关闭。每完成一个
能够独立解释的设计块，立即让 `$to-plan` 把结论写入活计划；然后重读总图、数据模型和时序，
统一实体名、状态名和读写方向。

**完成条件：**活计划已经用总图、核心数据模型和带数据变化的时序表达全部主流程；后续讨论
可以明确挂到某条流程、某个实体或一个共享执行边界。

## 3. 沿概要进入详细设计

以活计划为讨论地图，逐块深入跨边界载荷与接口、字段约束、状态转换、幂等与重试、并发、
配置和资源生命周期。这些是可能展开的面，不是必须产出设计产物的清单：并发、重试、幂等、
失败语义和资源生命周期各按[最小充分机制](references/minimal-mechanism.md)判必要性，结论可以
是「不处理」或「前置校验 + fail-fast」。只进入会改变实现选择的细节；当前代码事实和已有能力
在对应设计块中即时核对——提议新组件或新抽象前先确认现有代码不能满足，并在推荐答案中标明
实现重量与必要性。

进入精确目标契约前，让 `$to-plan` 完整执行其[设计块与契约深度](../to-plan/references/implementation-focus.md)
中的“确认来源门槛”；需要用户裁决的内容确认后再写入。每个详细设计块完成后立即回写，并
检查它是否确实细化了概要中的流程、实体或边界。

计划直接呈现所选设计，访谈过程和取舍理由只留在会话中。

**完成条件：**每项重要实现选择都有概要锚点和确认来源；计划中没有依赖会话记忆才能理解的
孤立细节。

## 4. 整体打磨与交付

所有设计块收敛后，让 `$to-plan` 执行全文打磨和独立审核。未决问题在文档外列给用户。

**完成条件：**首次阅读者能从概要顺着数据模型和时序进入细节；同一实体和状态贯穿图、表、
接口与实现定位。
