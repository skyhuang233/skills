# 注释规范

本文件定义实现过程中要写哪些注释、写到什么程度。被 `implement` 在流程开头要求完整阅读一次，
之后按类别查阅。

注释是设计工具，不只是文档：先写出接口注释，才能知道这个模块该对外说什么；写不出来，说明
接口还没想清楚。因此注释先于实现写出，而不是实现完成后补上。

## 覆盖范围

**每个类有接口注释，每个类变量有注释，每个方法有接口注释。**

例外只有一种：声明本身已经说清一切。getter 和 setter 有时属于此类。这是极少的情形，且必须是
有意识地省略——省略时要能说出省掉的是什么。默认省略不在此列。

## 四类注释

### 1. 接口注释

**位置：** 类、方法、函数或数据结构声明之前。

**写什么：**

- 类：这个类提供的整体抽象是什么，它在系统里承担什么角色。不是它有哪些步骤，也不是它的内部
  数据长什么样。
- 方法/函数：整体行为、参数及其含义、返回值、产生的副作用、抛出的异常，以及调用者在调用前
  必须满足的其他要求。

**关键约束：** 描述接口，不描述内部工作方式。读者不读实现就能正确使用它。

**反例**——把实现步骤写进了接口注释，调用者读到的信息对使用毫无帮助；同时漏掉了真正的接口
信息（失败了怎么办）：

```python
class TokenStore:
    """先查内存字典，没有再读文件，文件按行切分后逐行解析。"""
    def load(self, path: str) -> dict: ...
```

**正例**——一个抽象、参数语义、失败方式、不变量：

```python
class TokenStore:
    """持有一组已签发但尚未过期的 token，按主体 id 索引。

    token 一经 load 就不再变化；过期判断由调用者传入的时点决定，
    因此同一个 store 可以在不同时点上复用。
    """

    def load(self, path: str) -> dict:
        """从 path 读取 token 表，覆盖当前内容。

        文件不存在时返回空表；文件存在但格式非法时抛 `TokenFileError`，
        此时 store 保持原有内容不变。
        """
```

**写不出这条注释时：** 说明设计还没定。停下来改设计，不要用「处理 token 相关逻辑」这类模糊
注释绕过去。找不到诚实的名字和诚实的描述，通常是概念本身还没收敛（原则第 9 条）。

### 2. 数据结构成员注释

**位置：** 实例变量、静态变量的声明旁。

**写什么：** 这个字段代表的概念、单位、合法取值范围、它必须满足的不变量、是否可为空。

**关键约束：** 只写「它是什么」不够。读者需要这个信息才能判断赋值是否合法、读到某个值意味着
什么。缺了这条注释，读者只能从使用它的代码反推含义——而使用点通常分散在多处。

**反例：**

```typescript
class RetryPolicy {
  attempts: number;
  delay: number;
}
```

**正例：**

```typescript
class RetryPolicy {
  /** 总尝试次数，含首次调用。至少为 1。 */
  attempts: number;

  /** 首次重试前的等待毫秒数。后续重试按指数退避，上限 30_000。 */
  delay: number;
}
```

**特别注意：** 表示同一概念的多个字段必须写清它们之间的关系。「值为 0 表示不限」这类约定必须
写下来——否则调用者会把 0 当成「不重试」，而这两种含义恰恰是原则第 3 条要防的。

### 3. 实现注释

**位置：** 方法体或函数体内部。

**写什么：** 一个代码块在做什么、为什么这么做、依赖了什么不明显的前提。块注释写在块之前，
抽象层级高于它描述的语句。

**关键约束：** 不逐行复述代码。`// i 加一` 这类注释只增加噪音。与接口注释表达同一件事时不再
重复，只补接口注释里不明显、但对维护者有价值的点。

**反例**——复述代码：

```go
// 遍历 orders
for _, o := range orders {
    // 判断 status 是否等于 "paid"
    if o.Status == "paid" {
        // 加入 paid
        paid = append(paid, o)
    }
}
```

**正例**——解释不明显的前提和意图：

```go
// 上游按 created_at 升序返回，因此这里保持原顺序即可满足
// 「退款按支付顺序处理」的要求，不要改成并发处理。
for _, o := range orders {
    if o.Status == "paid" {
        paid = append(paid, o)
    }
}
```

**写作时机：** 在写代码块之前写它的注释。这会把「这一步到底要做什么」逼问清楚，再动手。若写完
注释发现它只是一句代码复述，说明这个块缺乏需要解释的意图——考虑它是否该被合并或删掉。

### 4. 跨模块注释

**位置：** 依赖关系两侧。

**写什么：**

- **依赖方**：我假设被依赖方提供什么、必须按什么顺序调用、它失败时我怎么办。
- **被依赖方**：谁依赖我这个行为。改这个行为会破坏谁。

**关键约束：** 两侧都要写。只写依赖方的假设时，被依赖方的维护者不知道有人在依赖它，一次看似
无害的「顺手优化」就会静默破坏调用者。

**反例**——依赖方靠调用顺序正常工作，但从代码里看不出来：

```typescript
class ReportBuilder {
  addRow(row: Row): void { /* 依赖 refresh() 之后再调用 */ }
  refresh(): void { /* ... */ }
}
```

**正例**——依赖方与提供方各写一句：

```typescript
class ReportBuilder {
  /**
   * 追加一行。必须在最近一次 refresh() 之后调用；refresh 会清空已追加的行。
   */
  addRow(row: Row): void { /* ... */ }

  /** 重建报表骨架并清空已追加的行。清空是契约的一部分，有调用方依赖它。 */
  refresh(): void { /* ... */ }
}
```

## 四条写作规则

1. **从调用者视角写。** 读者是下一个要使用或修改这段代码的人，不是编译器。写读者需要知道的
   事：怎么用、什么情况下会失败、什么不能碰。
2. **简短，抽象层级高于代码。** 几行足够。注释比它描述的代码低一个抽象层级时，它多半在复述。
3. **写不出来就是设计没定。** 停下来改设计，不要用模糊注释绕过（原则第 9 条）。
4. **注释随代码一起改。** 改方法体时接口注释对不上，是设计变了——回到注释上重新想，而不是
   把注释改成描述新实现。
