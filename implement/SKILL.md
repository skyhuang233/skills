# 实施

实现用户所描述的工作。输入不固定：可以指向 `.scratch/<feature>/plan.md`，也可以是一段
口述描述。先确认本次要实现的工作范围；若输入是 ticket 引用，本仓库没有 tracker 机制，
直接向用户询问。

**注释先于实现。** 开始前完整阅读 [注释规范](references/comments.md)，之后按类别查阅。
每个类有接口注释，每个类变量有注释，每个方法有接口注释。

## 1. 搭骨架

按下面的顺序写注释和声明，把结果直接落进目标源文件，方法体先用立即失败占位
（`NotImplementedError`、`todo!()`、`panic("not implemented")` 等，按语言惯例）：

1. 每个新类：写类接口注释；
2. 最重要的公有方法：写接口注释和签名，方法体留空；
3. 迭代这些注释，直到基本结构感觉正确；
4. 最重要的实例变量：写声明和注释。

骨架期间类型检查通过、运行即炸，这是预期状态，不是缺陷。**不要用返回零值或默认值的方法体
占位**——那会把「还没实现」伪装成「已实现」（第 2、3 条）。

**骨架只覆盖本次触碰的接口面。** 已有类上新增方法或字段时，只给新成员走上面的顺序；只改已有
方法的内部实现、签名不变时，不重写骨架，填方法体时同步更新它现有的接口注释。

这一步最容易违反第 6、8、9 条：抽象把内部结构暴露给调用者；名字说不清它做什么；找不到诚实
的名字仍硬起一个。写不出接口注释就是设计还没定——停下来改设计，不要用模糊注释绕过。

## 2. 填方法体

然后填写方法体，并在这个过程中：

- 发现需要新方法时，先写它的接口注释，再写方法体；
- 发现需要新变量时，在写声明的同时写它的注释；
- 每个代码块之前写它的实现注释。

当代码完成时，注释也已经完成。从来没有积压的待写注释。

这一步最容易违反第 1、2、3 条：用几个独立布尔拼状态机；缺失字段用默认值补上；带着已经无法
保证正确的状态继续运行。

## 3. 验证

定期跑类型检查、跑单个测试文件，最后跑一次全量测试。

收尾时把实现对照计划再读一遍，最容易违反第 5、19 条：为了通过检查而加不必要的抽象，或为
不存在的需求预留结构。

## 4. 审查并提交

完成后调用 `/code-review` 审查这次工作。

把工作提交到当前分支。
